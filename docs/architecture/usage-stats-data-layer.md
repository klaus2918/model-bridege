# 用量统计数据层（Rust）

> 目标：面板、API、配置文件、SQLite 表结构全部不变，降低统计端点的内存峰值与耗时，
> 并让「写入用量」不再被看板查询阻塞。

## 一、实现方式

| 维度 | 旧实现思路 | 当前 Rust 实现 |
|---|---|---|
| P50/P95 计算 | 把过滤后的全部 `duration_ms` 取回进程，排序、分组后再线性插值 | SQLite 窗口函数只定位 `floor(r*(n-1))` 与 `ceil(...)` 两个边界样本，Rust 只做插值 |
| 内存峰值 | 随过滤行数增长，多个统计端点并发时叠加 | 只物化每个分组的边界样本，内存与行数基本无关 |
| 连接模型 | 单连接 + 全局锁，读写互斥 | 1 条写连接 + 2 条只读连接（WAL），读不阻塞写 |
| 外部行为 | — | 字段、排序、数值、四舍五入口径不变 |

实现位置：`rust/model-gate/src/db.rs`（`percentile_cols` / `percentile_from_edges` /
只读连接轮转）；统计端点位于 `src/api_extra.rs`。

## 二、为什么这样改

1. **内存峰值来自「把明细搬进进程」**，不是 SQLite 本身。用量页每次刷新会并发请求
   totals / summary / models / upstreams 四个端点；旧实现每个端点都物化一份全量耗时
   列表，行数越大峰值越高，且会随并发叠加。
2. **百分位只需要两个样本**。`percentile()` 的线性插值只依赖第 `floor(r*(n-1))` 与
   下一个样本；这两个值可以在 SQLite 里用 `ROW_NUMBER()` / `COUNT(*) OVER ()` 直接定位。
3. **读写分离是 WAL 的自然用法**。看板聚合查询可能持续数百毫秒，单锁会让同一时刻完成的
   对话请求在「落库」这一步排队。当前实现固定 1 写 + 2 读：
   - 连接数固定，不随 HTTP 线程增长（内存可预期）；
   - 读连接只执行 SELECT，写连接负责 INSERT/UPDATE/DELETE；
   - 通过 `PRAGMA busy_timeout=5000` 处理极少见的写-写竞争。

## 三、兼容性约束

- `usage_records` / `settings` 表结构、索引、迁移逻辑未改动；旧库可直接打开。
- `Db::open` 以 `journal_mode=WAL` 启动；只读连接通过轮转选择，避免单连接热点。
- 百分位函数保留统一入口 `percentile_from_edges()`，所有统计端点共用同一插值口径。
- 统计接口字段与面板既有契约一致；不新增可独立演进的第二套统计源。

## 四、验证

- `cargo test`：数据层与统计端点单测（含 `today_stats_*` 缓存命中率用例）。
- `scripts/panel_api_smoke.ps1`：实例启动后检查统计端点可达与更新资源。
- 真机回归：面板用量页切换时间/上游/模型作用域，核对 KPI、趋势、明细与导出结果。

## 五、没有采用的方案

| 方案 | 不采用的原因 |
|---|---|
| 统计结果缓存 | 每条对话结束都会写库，缓存会被持续失效；在真实流量下收益不稳定，反而增加一致性问题 |
| 把全部明细加载到内存再排序 | 行数增长时内存与延迟不可控，且多个端点并发会叠加 |
| 引入第二套统计数据库 | 与「配置/用量唯一事实源」冲突，升级与备份复杂度上升 |
